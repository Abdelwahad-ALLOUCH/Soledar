SOLEDAR — Complete Game Development Blueprint
Master project specification
 Unity 6 LTS · 2D


We're going to turn Soledar from a basic Unity prototype into a complete indie game concept inspired by the exploration, atmosphere and combat of Hollow Knight, but with its own identity rooted in Moroccan architecture, history, landscapes, folklore-inspired fantasy and visual culture.

My recommendation: give your AI agent the specification below and ask it to develop the project in phases, testing every system before moving forward.

One important distinction: don't ask an agent to generate the entire game in one operation. It should build a playable vertical slice first, then expand the world. That will prevent the kind of broken dependencies and physics issues we encountered earlier.

1. Game identity






















17














SOLEDAR
Echoes of a Forgotten Kingdom

Genre: 2D Action Metroidvania / Dark Fantasy

Engine: Unity 6 LTS (6000.3.4f1)

Perspective: 2D side-scrolling

Platform: PC first, with controller support and possible console releases later.

Visual direction: Hand-drawn 2D environments, atmospheric lighting, expressive character animation and Moroccan-inspired architecture.

The central concept
The player controls Soledar, a mysterious masked wanderer carrying an ancient curved blade called the Ashen Khoumya.

He explores a forgotten kingdom buried beneath centuries of sand, where abandoned medinas, ruined kasbahs, underground sanctuaries and forgotten civilizations remain.

The kingdom is not simply abandoned. Something happened to it.

The player gradually discovers that the kingdom's silence, its strange inhabitants and its decaying architecture are connected to an ancient event.
What makes Soledar different?
- Moroccan architecture is part of the actual level design, not just decorative textures.
- Zellige patterns can represent magical mechanisms and ancient technology.
- Different Moroccan-inspired regions have distinct gameplay mechanics.
- Traditional instruments and atmospheric sound design create a unique identity.
- The story is discovered through exploration, environmental details and NPC interactions.
- The protagonist has an evolving combat and traversal system.

The game should have a strong gameplay foundation before adding large amounts of content.

Movement requirements
- Responsive controls.
- Consistent physics.
- No unwanted acceleration after a dash.
- No infinite wall climbing.
- Proper collision detection.
- Separate ground and wall detection.
- Controller and keyboard support.
- Configurable movement values in the Inspector.

4.4 Health and healing
Implement a health system based on masks rather than ordinary hearts.
- Initial health: 5 masks.
- Health upgrades increase maximum masks.
- Taking damage removes one mask.
- Healing restores one or more masks.
- Temporary invincibility after receiving damage.
- Death triggers a respawn sequence.
- Healing consumes an energy resource.
Later, add an upgrade system that allows players to improve maximum health.
4.5 Energy system
Introduce a resource called Echo Energy.

The player collects energy by:
- Hitting enemies.
- Defeating bosses.
- Discovering ancient objects.
- Finding hidden energy fragments.
Energy can be spent on:
- Healing.
- Magical attacks.
- Special abilities.
- Certain environmental mechanisms.

Architecture recommendations
The agent should use:

1. Component-based architecture

Separate movement, health, combat, abilities, animation and interaction.

2. ScriptableObjects

Use data assets to configure:
- Enemy statistics.
- Weapon damage.
- Ability costs.
- Item descriptions.
- Boss attack parameters.
- Quest requirements.
3. State machines

Use explicit states for:
- Player movement.
- Player combat.
- Enemy AI.
- Boss behavior.
- Dialogue interactions.
4. Event-driven communication

Use events for:
- Player health changes.
- Enemy death.
- Boss defeat.
- Currency changes.
- Ability unlocks.
- Quest completion.
- UI updates.
5. Scene management

Use a Bootstrap scene and a controlled scene-loading system. Avoid having every scene independently initialize duplicate managers.
Important technical rules
- Use Unity 6-compatible APIs.
- Use Rigidbody2D.linearVelocity consistently in Unity 6.
- Read input in Update() and apply physics in FixedUpdate().
- Do not mix physics movement with arbitrary Transform movement.
- Use collision layers and masks consistently.
- Avoid unnecessary FindObjectOfType calls.
- Avoid hardcoded scene names throughout scripts.
- Avoid duplicate singleton managers.
- Never put all gameplay functionality in one script.
- Provide null-reference checks and meaningful error messages.
- Keep all Inspector references documented.
- Make important parameters configurable.
- Use object pooling for frequently spawned effects where beneficial.

18. Performance and optimization
Even though the game is initially PC-only, performance should be considered from the beginning.

Requirements:
- Target 60 FPS minimum.
- Support different screen resolutions.
- Avoid unnecessary Update loops.
- Use object pooling for repeated effects.
- Optimize particle systems.
- Use appropriate texture compression.
- Use sprite atlases where beneficial.
- Avoid excessive real-time lights.
- Optimize tilemap colliders.
- Avoid excessive physics queries.
- Use asynchronous scene loading where appropriate.
- Profile CPU, GPU and memory usage.

22. How the AI agent should work
This section is critical. An AI agent can generate a lot of code, but without development rules it can also destroy an existing project, create duplicate systems or leave scripts disconnected.

Give it these rules.
Agent development rules
1. Inspect before modifying: Examine the existing Unity project, scripts, scenes, prefabs and components before making changes.
2. Preserve working functionality: Do not unnecessarily replace existing movement, jumping, dash, attack, health or UI systems.
3. Work incrementally: Complete one development phase at a time.
4. Test every feature: Do not declare a feature complete just because its script compiles.
